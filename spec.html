CLEARGLASS Guardian Command Nexus Specification

SPEC‑1: CLEARGLASS Guardian Command Nexus

1. Purpose and Scope

The Guardian Command Nexus is the central command‑and‑control dashboard for CLEARGLASSINC’s GUARDIAN suite. It is a single‑page web application that provides operators with real‑time oversight of security workflows, simulated environments and system health. Its cyberpunk aesthetic hides a sophisticated architecture that orchestrates reactive state management, simulations, audit logging and AI‑driven command routing.

The purpose of this specification is to clearly define the initial production version, inform refactoring of the existing prototype, and provide a base for future extension. In scope are the modules already present in the current HTML artifact—shell kernel, reactive state fabric, simulation grid, audit ledger, operator routing and AI command orchestration—as well as their integration points. Out of scope are detailed implementation of third‑party integrations (e.g. PowerShell modules) or platform‑specific deployment scripts; these may be defined in later specs.

2. System Overview

The Command Nexus is architected as a client‑side SPA built with modern JavaScript (ES6+) and an application framework (assumed to be React or Vue given the prototype’s reactive state fabric). The application bootstraps a shell kernel that coordinates all subsystems and exposes a command bus to the UI. A state fabric holds canonical application state and broadcasts changes via events. A simulation grid synthesises sensor and environmental data at a configurable cadence to drive dashboards and AI reasoning. An audit ledger records all operator actions and system events with severity levels and metadata. AI command orchestration parses natural‑language intents from operators or connected systems and translates them into structured actions. Operator routing provides navigation between views (Dashboard, Pipeline, Surveillance, Tasks, AI Console, System) and orchestrates hotkeys and quick actions. The visual layer comprises responsive panels, charts and terminal components consistent with the cyberpunk console aesthetic.

The HTML front end communicates with back‑end services via internal APIs. For the initial version these may be mocked or stubbed; the specification assumes eventual REST or GraphQL endpoints for persistence (audit log export, state snapshots), AI inference and external data feeds. External systems (e.g. network scanners, SOC tools) will integrate through defined interfaces but are not implemented in this revision.

3. Core Requirements

3.1 Functional Requirements

  • Dashboard view: Display high‑level metrics from the simulation grid and real operations. Operators can interact with widgets to drill down into pipeline tasks, surveillance feeds and incident timelines.
  • Pipeline view: Visualise and manage workflows such as network scans, security automation or predictive analysis. Tasks move through stages with status indicators.
  • Surveillance view: Present live or simulated sensor feeds (e.g. CCTV, network traffic). Operators can control playback and adjust filters.
  • Tasks view: List assigned tasks, alerts and incidents with sorting and filtering. Operators can acknowledge, snooze or transfer tasks.
  • AI console: Accept natural‑language commands, display parsed intents and proposed actions, and allow operators to confirm execution. Provide a transcript of AI conversations.
  • System view: Show system health (CPU, memory, network) and log messages. Allow administrators to start/stop subsystems.
  • Audit logging: Record all operator actions (navigation, confirmations, command executions), AI actions, and system events with timestamp, severity and context.
  • State persistence: Persist state fabric snapshots and audit ledger entries to local storage or back‑end services. Support schema versioning to handle migrations.
  • Simulation controls: Provide settings to adjust simulation cadence, toggle stochastic/deterministic mode and seed values.

3.2 Non‑Functional Requirements

  • Performance: The dashboard should render initial content within 2 seconds on modern browsers and maintain 60 fps during interaction. Simulation updates should not block UI rendering.
  • Reliability: The shell kernel must recover gracefully from subsystem failures. Unhandled exceptions should be captured by the audit ledger and displayed in the System view.
  • Usability: The interface shall support keyboard navigation and screen‑reader labels. Hotkeys must not conflict with browser shortcuts.
  • Maintainability: Code should be modularised by subsystem with typed interfaces. Event names and payload shapes should be centralised. Tests should cover reducers, command parsing and critical UI flows.
  • Extensibility: New views and AI intents should be pluggable without changing core modules. The spec defines clear extension points for PowerShell integration and SOC workflows.

3.3 Scalability Considerations

The simulation grid and AI routing may grow as new sensors and models are added. Architect the state fabric so that data entities are normalised and keyed by stable identifiers. External service calls must be asynchronous with timeout and retry logic. Logging should be batched for export rather than writing per event.

4. Domain Model

The domain is centred on events generated by the simulation, operator actions, AI commands and external systems. The following entities capture domain concepts:

Entity Description Fields / Notes
Task Represents a unit of work in the pipeline (e.g. network scan, report generation). id, name, type, status, assignedTo, createdAt, updatedAt, dueAt, parameters (object), logs (array of references)
Alert Generated when simulation or monitoring detects an anomaly. id, severity, source (simulation sensor, external feed), description, timestamp, acknowledgedBy, relatedTaskId
Incident Collection of related alerts or tasks that constitute a security incident. id, name, description, startTime, endTime, alerts (array of alert ids), tasks (array of task ids), status, owner
TimelineEvent Ordered events displayed on dashboards and surveillance views. id, type, timestamp, data (arbitrary JSON), relatedId (task/incident/alert), displayLabel, severity
AuditEntry Immutable record of an action or system event. id, timestamp, actor (operator username or system), action (string key), context (object), severity, correlationId
SimulationState Holds state of simulated environment at a given tick. tick, readings (map of sensor name → value), activeEntities (list of simulated objects), seed, mode (deterministic|stochastic)
OperatorSession Captures logged‑in user’s session for routing and state restoration. userId, roles, startTime, endTime, viewPreferences, hotkeyBindings, activeTasks (list of task ids)
AIIntent Parsed intent from the AI command orchestration. id, input (raw text), intentType, entities (map), confidence, proposedActions (array), resolved (boolean), resolutionNotes

Entities are stored in the state fabric keyed by id; relations are maintained through reference fields. Ownership of state follows these rules:

  • Operator client: Maintains transient UI state (collapsed panels, unsaved form inputs) and active tab.
  • State fabric: Owns canonical domain entities; updates occur only through reducers triggered by dispatched events. No module writes state directly.
  • Back‑end services: Persist long‑term state (audit log, snapshots) and provide data to simulation or AI modules. The front end writes via API calls.

5. AI Command Orchestration

AI command orchestration converts natural‑language instructions into structured commands executed by the system. The module comprises a parser, an intent classifier, and an execution planner.

5.1 Intent Handling Model

  1. Input acquisition: Operator types or speaks a command in the AI console.
  2. Pre‑processing: Text is normalised (case‑folding, punctuation removal) and tokenised. A local model or cloud service classifies the intent type and extracts entities (target task, time range, severity, etc.).
  3. Intent representation: The parser produces an AIIntent object. Example intents include create_task, escalate_alert, summarize_incident, adjust_simulation, query_state, execute_powershell (future extension).
  4. Confirmation dialog: For intents with side effects, the console presents a summary of proposed actions and awaits operator confirmation.
  5. Execution: Upon confirmation, commands are dispatched through the shell kernel to relevant subsystems (e.g. state fabric for task creation, pipeline orchestrator for workflow changes).
  6. Feedback: Results, success or error messages are returned to the AI console, appended to the transcript and logged in the audit ledger.

5.2 Command Parsing Approach

For the initial implementation, a rule‑based parser suffices. A mapping table translates imperative verbs to intent types and uses regular expressions to extract entities. For example:

Example input Detected intent Extracted entities
“Run a network scan on subnet 10.0.0.0” create_task { taskType: "networkScan", target: "10.0.0.0" }
“Escalate all high severity alerts” escalate_alert { severity: "high" }
“Summarize the last incident report” summarize_incident { incidentScope: "last" }

Ambiguities are resolved by asking clarifying questions: if multiple tasks match “Run the scan again,” the system lists candidates and requests selection. Unknown intents trigger an error message with guidance.

5.3 Error Handling and Ambiguity Resolution

  • Unknown verbs or malformed commands produce a unrecognized_intent with an explanatory message.
  • Missing required entities prompt the operator to supply the missing information.
  • Execution errors (e.g. network call failures) are surfaced to the operator and recorded in the audit ledger at severity = error.
  • Timeouts in AI inference result in retries up to three times; after which a timeout response is returned.

6. Reactive State Fabric

6.1 Store Design

The state fabric follows a unidirectional data flow pattern. A single store holds all domain entities in normalised form. Actions dispatched on the shell kernel are processed by reducers that compute new state snapshots without mutation. Views subscribe to selectors that derive data slices and re‑render when relevant state changes.

State is partitioned into logical modules:

Slice Contents
tasks Map of task ID → Task
alerts Map of alert ID → Alert
incidents Map of incident ID → Incident
timeline Ordered list of TimelineEvent
audit Append‑only list of AuditEntry (may be stored separately for performance)
simulation Current SimulationState and history buffer
operator OperatorSession information
ai Current AI console state (input text, list of AIIntent, transcript)

6.2 Events, Reducers, Selectors and Subscriptions

  • Events (actions): Named messages with type and payload (e.g. TASK_CREATE, ALERT_ACKNOWLEDGE, AI_INTENT_RESOLVED). Event names are namespaced (e.g. ai/intentResolved).
  • Reducers: Pure functions that accept current state and an event payload and return a new state. Each slice may have its own reducer composition but uses a shared schema version constant.
  • Selectors: Functions that derive computed data for components, memoised for performance. For example, selectActiveAlertsBySeverity(state, severity) returns filtered alerts.
  • Subscriptions: UI components and subsystems subscribe to relevant selectors. When state updates, subscribers re‑evaluate selectors and update the UI.

6.3 Persistence Strategy and Schema Versioning

State snapshots and audit logs must be persisted for recovery and analysis. The front end serialises the state fabric (excluding transient UI state) to localStorage or IndexedDB on intervals and upon critical events (e.g. navigation away). A schemaVersion field is stored along with the data. When loading persisted state, the shell kernel checks the version; if mismatched, a migration script transforms old data to the current schema. Audit ledger entries are written to a separate storage area for efficient append. Exporting the audit ledger triggers a synchronous retrieval of all entries and sends them to a back‑end API for archival.

7. Simulation Grid

The simulation grid models environmental and system processes to provide realistic data streams in the absence of live feeds. It can simulate sensor readings (temperature, bandwidth usage, CPU load), adversarial behaviours (intrusion attempts, DDoS patterns) and pipeline tasks (scans, automations).

7.1 Update Cadence

A scheduler in the shell kernel triggers simulation updates at a configurable interval (default: 1 second). Each tick advances the tick counter, updates sensor readings based on deterministic or stochastic functions, and emits SIMULATION_UPDATE events with the new SimulationState. The update cadence should be adjustable via the System view.

7.2 Deterministic vs Stochastic Behaviour

Operators can toggle the simulation mode:

  • Deterministic: Uses fixed seed and predictable progression. Useful for demos and regression testing.
  • Stochastic: Adds noise and random events using seeded RNG. Suitable for training and stress testing.

Sensor models should be encapsulated in discrete functions that accept seed, tick and parameters and output values. New models can be added without modifying the scheduler.

7.3 Impact on UI and AI Output

Simulation updates drive the data visualised in dashboards and may generate alerts or incidents when thresholds are crossed. The AI command orchestration can query simulation state to answer operator questions such as “What is the current CPU load?” Therefore, the simulation grid must publish its state through the state fabric and allow query by selectors. When the simulation triggers events (e.g. simulated intrusion), corresponding actions (e.g. ALERT_CREATE) are dispatched.

8. Audit Ledger

The audit ledger is a tamper‑evident log of events for accountability and post‑mortem analysis.

8.1 What Gets Logged

  • Operator actions: Navigation changes, form submissions, AI intent confirmations, task assignments, acknowledgement of alerts.
  • System events: Simulation updates, pipeline transitions, subsystem errors, configuration changes.
  • Security events: Login/logout, permission changes, failed authentication attempts.
  • AI interactions: Raw command text, parsed intent, execution results and errors.

Each entry includes a severity level (info, warning, error, critical) and may reference related entities via correlationId for cross‑linking in UI.

8.2 Retention and Export Strategy

Audit entries are persisted locally for the duration of the operator session and periodically flushed to a back‑end service. The export process groups entries by date and severity and uploads in batches to minimise network overhead. An operator can initiate a manual export through the System view. Retention policy is configurable (e.g. keep last 10 days on client), and expired entries are purged once exported.

8.3 Relationship to Security and Operator Actions

The audit ledger forms part of the security boundary: destructive actions (e.g. deleting tasks, executing PowerShell commands) must require explicit confirmation and generate high‑severity audit entries. The ledger should be write‑only from the perspective of modules; only the System view has read access for display. Permissioning is enforced such that only administrators can export or clear logs.

9. Operator Routing and UX

The operator routing subsystem manages navigation and user experience across the various views.

9.1 Tabs, Views and Hotkeys

  • Views: dashboard, pipeline, surveillance, tasks, aiConsole, system. The shell kernel maintains the active view in the operator slice.
  • Tabs: Represent open contexts within each view (e.g. multiple task details). Tabs can be closed or rearranged.
  • Hotkeys: Provide rapid actions: e.g. Ctrl+1..Ctrl+6 to switch views, Ctrl+/ to focus on AI console, Ctrl+S to save state snapshot. Hotkey bindings are configurable in operator preferences.

9.2 Boot Sequence and Loading States

Upon page load, the shell kernel executes a boot sequence:

  1. Initialise state fabric with default schema and attempt to hydrate from persisted snapshot.
  2. Start simulation grid and load any saved seed/mode settings.
  3. Initialise audit ledger and log SYSTEM_BOOT event.
  4. Launch AI command module and load conversation history if available.
  5. Render UI components once core modules are initialised. Display loading indicators and error messages if subsystems fail to start.

9.3 Accessibility and Operator Feedback

The UI must support ARIA roles for screen readers. Colour choices should meet WCAG 2.1 contrast ratios. Error and success notifications should appear in an accessible toast component. Feedback from AI commands should clearly differentiate between system messages, AI suggestions and operator actions. Operators should receive confirmation dialogues for actions with side effects. Focus management must ensure modals trap focus until dismissed.

10. Integration Interfaces

10.1 Internal APIs between Subsystems

The shell kernel exposes a set of event names and payload shapes that subsystems use to interact.

Event Name Payload shape Description
task/create { name, type, parameters } Request creation of a new Task. Reducer allocates id and adds to store.
task/updateStatus { id, status } Update a task’s status; triggers pipeline update and audit entry.
alert/acknowledge { id, actorId } Mark an alert as acknowledged by an operator.
incident/resolve { id, resolutionNotes } Mark an incident as resolved and log outcome.
simulation/update { tick, readings, activeEntities } New simulation state from grid. Used by selectors to update charts.
ai/intentParsed { intentId, intentType, entities, confidence } AI parser output; triggers display of proposed actions in AI console.
ai/intentConfirmed { intentId } Operator confirms execution; dispatch to appropriate event (task/create, etc.).
audit/log { actor, action, context, severity } Append entry to audit ledger.
router/navigate { view, params } Switch active view or open context tab.

10.2 External Interfaces

The initial implementation can stub external services. Anticipated REST endpoints include:

  • POST /api/audit/export – Accepts a batch of AuditEntry and returns status.
  • GET /api/state/snapshot – Returns latest persisted state for hydration.
  • POST /api/ai/parse – Submits natural‑language input and returns AIIntent. In early versions this may be handled locally via rule‑based parser.
  • POST /api/powershell/execute – Executes a PowerShell script (future extension). Secured and audited.

Event payloads exchanged with external services should be JSON encoded using camelCase keys. All requests include an authentication token (to be defined in security spec) and handle 401/403 responses by routing to login.

11. Security and Safety

The Guardian Command Nexus must operate within strict security boundaries.

  • Trust boundaries: The browser front end is untrusted; back‑end services validate all inputs and enforce permissions. Only authorised operators may access sensitive views (e.g. incident details). CORS and CSP headers restrict loading of external resources.
  • Safe execution: Destructive actions (deleting entities, executing commands) require confirmation with a summary of the impact. Confirmation dialogues are modal and default to cancel.
  • Logging and permissioning: The audit ledger logs all actions with actor identity. Role‑based access controls restrict features (e.g. only administrators can export logs or change simulation mode). Passwords or secrets are never logged.
  • Data protection: Persisted data is encrypted at rest when stored server‑side. Transmission uses HTTPS with TLS 1.2+. Operators are automatically logged out after configurable inactivity.
  • Input sanitisation: All user inputs are escaped to prevent injection attacks. AI command parsing ensures that executed commands are within allowed actions; arbitrary code execution (e.g. PowerShell) is disabled in the first version.

12. Acceptance Criteria

The first production‑ready release of the Guardian Command Nexus shall satisfy the following conditions:

  1. All views implemented: Dashboard, Pipeline, Surveillance, Tasks, AI Console and System views render correctly, switching via navigation or hotkeys.
  2. State management: Actions correctly update the state fabric; selectors drive UI updates without direct mutation.
  3. Simulation: Simulation grid generates data at configurable cadence and mode; dashboards reflect changes in real time.
  4. AI console: Accepts natural‑language input, produces parsed intents via rule‑based parser, and executes confirmed commands, logging all actions.
  5. Audit logging: All operator and system events recorded with severity and persisted; export function uploads logs.
  6. Error handling: Subsystem failures are surfaced in System view; unhandled errors do not crash the application.
  7. Accessibility: UI meets minimum WCAG 2.1 level AA requirements; keyboard navigation and screen reader labels are provided.
  8. Tests: Unit tests cover reducers, simulation models, command parsing and routing; integration tests cover critical flows.

13. Future Extensions

13.1 Suggested Next Milestones

  1. PowerShell Integration: Define and implement secure execution of PowerShell scripts from AI commands. Provide a sandboxed environment and extend audit logging to capture command outputs.
  2. SOC Workflow Integration: Integrate with Security Operations Centre tools (e.g. SIEM) to ingest real events and enrich simulation. Define connectors and mapping to domain entities.
  3. Predictive Analysis and Anomaly Detection: Incorporate machine learning models to predict incidents based on historical data and simulation patterns. Present predictions in the dashboard with confidence intervals.
  4. Reporting Module: Generate PDF or HTML reports summarising incidents, audit logs and simulation statistics. Provide scheduling and export options.
  5. Collaboration Features: Enable multiple operators to collaborate, share annotations and transfer tasks. Implement WebSocket sync of state changes.

13.2 Modularisation Roadmap

The current monolithic front end should be decomposed into packages: core (shell kernel, state fabric), ui (components and styling), simulation, ai, audit, and integrations. Each package exposes public APIs and can be independently tested. Use TypeScript to add type safety and facilitate refactoring.

13.3 Potential Enhancements

  • Pluggable AI intents: Allow external providers to register new intent handlers via configuration.
  • Visual theming: Support dark/light modes and custom themes while preserving the console aesthetic.
  • Mobile responsiveness: Adapt layouts for tablet and small screens without losing functionality.
  • Advanced analytics: Integrate streaming analytics dashboards (e.g. Grafana) for real‑time metrics.

Implementation Priority

  1. Core Framework and State Fabric: Establish the shell kernel, event bus, reducers, selectors and routing. Implement domain models and ensure persistence with schema versioning. Without this foundation, other modules cannot be integrated.
  2. Simulation Grid and Dashboard: Build the simulation scheduler and sensor models, and render dashboard widgets. Provide controls for cadence and mode. This enables demonstrable value early and facilitates testing of state updates and rendering.
  3. AI Command Orchestration: Implement the rule‑based parser, console UI and command execution flow with confirmation dialogues. Connect to state fabric and logging. This unlocks advanced interactions and sets the stage for future PowerShell and SOC integrations.
